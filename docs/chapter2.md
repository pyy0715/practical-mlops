# Understanding MLOps

## Beyond DevOps

모델을 어디에서 실행하고, 데이터를 어떻게 전달하고, 다른 서비스와 어떻게 연결할 것인가는 모델을 훈련하는 것만큼 중요하다. 배포한 뒤에도 시간이 지나면서 성능이 달라질 수 있다. MLOps는 이 변화를 발견하고 다음 개선으로 연결하는 운영 방식이다.

DevOps의 자동화와 CI/CD 원칙은 여기에서도 유효하다. 다만 머신러닝에서는 코드 외에 데이터와 모델도 검증하고 관리해야 한다. 코드가 그대로여도 입력 데이터가 달라지면 예측 품질이 떨어질 수 있기 때문이다. Google의 [MLOps 문서](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning)도 데이터 및 모델의 검증과 지속적 훈련을 주요 차이로 설명한다.

**서비스가 정상 응답하는지와 모델이 여전히 유효한 예측을 하는지는 함께 확인해야 한다.**

## Data and Lineage

데이터는 수집한 양만으로 판단하기 어렵다. 언제, 어디서, 어떤 기준으로 수집했고 어떤 변환을 거쳤는지 알아야 사용할 수 있는 범위를 판단할 수 있다. 특정 고객군에서만 모은 데이터를 전체 고객의 특성으로 받아들이면 문제 정의부터 어긋날 수 있다.

EDA는 이런 한계와 패턴을 확인하는 과정이다. 결측치와 이상치를 살피는 데서 나아가, 확보한 데이터로 원래의 질문에 답할 수 있는지 검토해야 한다. 데이터가 부족하다면 모델을 바꾸기 전에 수집 범위나 목표를 조정할 수 있다.

리니지는 이 판단과 변경의 경로를 연결한다. 원본 데이터와 전처리, 피처, 훈련 실행, 모델 버전을 이어 두면 결과가 달라졌을 때 어디서 변화가 시작됐는지 추적할 수 있다. **재현성은 모델 파일을 보관하는 데서 끝나지 않고, 그 모델을 만든 조건을 다시 확인할 수 있어야 성립한다.**

## Evaluation and Deployment

평가 기준은 비즈니스에서 어떤 오류를 더 크게 보는지에 따라 달라진다. 사기 탐지라면 사기를 놓치는 손실과 정상 거래를 차단하는 불편을 함께 고려해야 한다. 전체 평균이 좋아져도 특정 고객군이나 입력 조건에서 성능이 떨어진다면 배포 판단은 달라질 수 있다.

일부 조직에서는 예측의 근거를 설명하는 것도 필요하다. [LIME](https://arxiv.org/abs/1602.04938)은 개별 예측 주변에서 모델의 동작을 근사하고, [SHAP](https://shap.readthedocs.io/en/latest/generated/shap.plots.waterfall.html)은 피처별 기여를 통해 예측 결과를 설명한다. 이런 분석은 점수만으로 드러나지 않는 모델의 의존성과 오류를 살피는 데 도움이 된다.

배포 환경도 평가의 일부다. API로 요청을 처리하는 모델과 에지 디바이스에서 실행하는 모델은 지연시간과 자원 제약이 다르다. 양자화 같은 최적화를 거쳤다면 최종 배포할 모델을 실제 환경에서 다시 검증해야 한다.

Spotify의 [홈 추천 모델 운영 사례](https://engineering.atspotify.com/2021/11/the-rise-and-lessons-learned-of-ml-models-to-personalize-content-on-home-part-ii)(2021)에서는 모델과 규칙 기반 추천을 같은 평가 로직과 데이터로 비교하는 데 어려움을 겪었다. 팀은 별도의 평가 파이프라인을 만들고, 입력 피처에 따른 실제 추천 결과를 비교하는 대시보드도 사용했다. 이를 통해 서로 다른 입력에도 같은 콘텐츠를 추천하는 문제를 배포 전에 발견했다.

**평가 자동화에는 모델 간 점수 비교뿐 아니라, 기준선보다 나아졌는지와 실제 결과가 의도대로 나오는지를 확인하는 과정도 포함되어야 한다.**

## Monitoring and Feedback

운영에서는 시스템과 예측 품질을 함께 관찰해야 한다.

| 관찰 대상 | 확인할 내용 |
| --- | --- |
| 서비스 | 오류율, 지연시간, 처리량, 자원 사용량 |
| 데이터 | 결측치, 스키마 변화, 피처 분포 변화 |
| 예측 | 예측값 분포, 정답이 확보된 뒤의 성능, 주요 집단별 오류 |

데이터 드리프트는 성능 저하를 의심할 신호다. 바로 재훈련하기보다 수집 오류인지, 전처리가 달라졌는지, 실제 사용 환경이 변했는지 확인해야 한다. 재훈련으로 해결할 문제와 데이터 파이프라인을 수정해야 할 문제는 다르다.

카카오페이의 [「FDS에 지속 성장하는 ML 모델 적용 이야기」](https://tech.kakaopay.com/post/ifkakao2024-fds/)(2024)는 이런 대응을 구체적으로 보여준다. 최근 데이터로 주기적으로 재훈련하고, 운영 모델과 Recall, Precision, FP 등을 비교해 개선된 모델을 배포할 수 있도록 했다. 여기에 “결제 아이템 종류별 최근 사고 비율”을 피처로 사용해, 새로운 사고 정보가 재훈련 전에도 예측에 반영될 수 있도록 구성했다.

**운영 피드백은 재훈련뿐 아니라 피처 갱신과 모델 검증에도 연결되어야 한다.** 변화에 대응하는 경로가 갖춰져야 머신러닝 수명주기가 운영 루프로 작동한다.

## MLOps Maturity

Google은 자동화 범위에 따라 MLOps 성숙도를 세 단계로 구분한다.

| 수준 | 운영 방식 | 핵심 변화 |
| --- | --- | --- |
| Level 0 | 실험, 훈련, 모델 전달을 수동으로 수행 | 훈련된 모델을 배포 |
| Level 1 | 데이터 및 모델의 검증을 포함한 훈련 파이프라인 자동화 | 모델을 만드는 흐름을 배포 |
| Level 2 | 파이프라인 자체의 빌드, 테스트, 배포 자동화 | 그 흐름의 변경도 지속적으로 전달 |

![Google의 MLOps Level 1 훈련 파이프라인 자동화](https://docs.cloud.google.com/static/architecture/images/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning-3-ml-automation-ct.svg)

*출처: Google Cloud, 「MLOps: Continuous delivery and automation pipelines in machine learning」*

Level 1에서는 실험과 운영에 같은 파이프라인 구현을 사용하고, 메타데이터와 실행 트리거를 연결한다. Level 2에서는 파이프라인 코드의 변경까지 검증하고 배포한다. 도구를 더 설치하는 것보다 반복되는 전달 과정에서 수작업과 오류를 줄이는 것이 중요하다.

이 과정에는 팀 간 합의도 필요하다. 데이터 사이언티스트의 평가 결과, 엔지니어의 운영 지표, 비즈니스 담당자의 성공 기준이 연결되어야 배포와 재훈련을 결정할 수 있다. 데이터와 모델의 소유자, 배포 승인 기준, 이상 발생 시 대응 책임도 명확해야 한다.

**MLOps의 성숙도는 새 모델을 얼마나 자주 만드는지와 함께, 변경을 얼마나 검증 가능하고 복구 가능한 방식으로 운영하는지에서 드러난다.**
